# Code Patterns

Most patterns are enforced by ESLint (`eslint.config.js`). Rules that aren't mechanically enforceable are listed here with the reasoning so the LLM can apply them correctly to novel cases.

## JavaScript

**Arrow functions only — no `function` declarations or expressions.**

```ts
// ✓
const normalize = (s: string) => s.trim().toLowerCase();
export const useMyHook = () => { ... };

// ✗ — func-style rule (enforced)
function normalize(s: string) { ... }
export function useMyHook() { ... }
```

**No `for` loops — use array methods.**

```ts
// ✓
const totals = items.map((item) => item.price * item.qty);
const active = items.filter((item) => item.enabled);
items.forEach((item) => process(item));
const sum = items.reduce((acc, item) => acc + item.price, 0);

// ✗ — no-restricted-syntax rule (enforced)
for (const item of items) { ... }
for (let i = 0; i < items.length; i++) { ... }
```

**Avoid mutations — prefer immutable transforms.**

ESLint catches property mutations on function parameters (`no-param-reassign`). Mutations to local variables aren't caught mechanically, so apply this rule by judgment:

```ts
// ✓
const byCategory = items.reduce<Record<string, Item[]>>(
  (acc, item) => ({ ...acc, [item.category]: [...(acc[item.category] ?? []), item] }),
  {}
);

// ✗ — accumulator mutation, also caught by no-param-reassign
const byCategory = items.reduce(
  (acc, item) => {
    if (!acc[item.category]) acc[item.category] = [];
    acc[item.category].push(item);
    return acc;
  },
  {} as Record<string, Item[]>
);
```

Exception: calling methods on a Map/Set accumulator (`map.set(...)`, `set.add(...)`) is acceptable — these are method calls, not property assignments, and do not trigger `no-param-reassign`.

**Avoid `let` + deferred assignment.**

`prefer-const` catches `let` that could be `const`. The harder case — `let x; x = computeValue()` — is a code smell even when `x` is genuinely reassigned. Prefer:

```ts
// ✓
const status = isActive ? 'active' : 'inactive';
const label = (() => {
  if (score > 90) return 'excellent';
  if (score > 70) return 'good';
  return 'needs work';
})();

// ✗ — avoid this pattern
let status;
if (isActive) {
  status = 'active';
} else {
  status = 'inactive';
}
```

## TypeScript

**`type` not `interface` — consistent-type-definitions rule (enforced).**

**No type casts (`as X`) — no-non-null-assertion rule enforced for `!`.**

When TypeScript can't narrow a type automatically (e.g., after `.filter()`, or with Supabase RPC return types), use:

1. Type predicates for filter: `items.filter((x): x is Defined => x !== null)`
2. Zod for external/DB data (see Supabase section below)
3. `?? fallback` instead of `!` for nullable values

```ts
// ✓
const value = maybeValue ?? defaultValue;
const items = list.filter((x): x is Item => x !== null);

// ✗ — both enforced by ESLint
const value = maybeValue!;
const typed = rawData as Item;
```

## React

**Assess reusable components before writing inline JSX.**

Before writing a new block of JSX, check: does a component in `src/features/ui/` already handle this? Would extracting this into a new component make the call site 3+ lines shorter or the logic clearly reusable? If yes, create or use the component.

If a component would only be used once and doesn't simplify the call site, inline it.

**Event handlers as named consts, not inline arrows on JSX props.**

```tsx
// ✓
const handleSubmit = () => { ... };
<button onClick={handleSubmit}>Submit</button>

// ✗ — acceptable for trivial one-liners but prefer named for anything non-trivial
<button onClick={() => { doThing(); doOtherThing(); }}>Submit</button>
```

## react-query

**One file per query or mutation function** — placed in `hooks/` alongside the component that uses it.

```
src/features/practice/hooks/
  useBuildPracticeSession.ts   ← useQuery wrapper
  useRecordPracticeAnswer.ts   ← useMutation wrapper
```

**Always destructure the hook return.**

```ts
// ✓
const { data, isLoading, error } = useBuildPracticeSession();
const { mutate, isPending } = useRecordPracticeAnswer();

// ✗
const result = useBuildPracticeSession();
result.data; // harder to read, misses loading/error handling
```

**Always handle loading and error states** — don't render data without guarding both.
**Always handle loading states of with loading components like circular progress** — don't render data without loading states.

## Supabase

**Never modify `src/api/schema.ts`.** It is generated by `pnpm update-types` from the live DB schema. Run that command after any SQL migration.

**Use Zod to narrow DB types at the boundary.**

Supabase generated types are broad (e.g., `string` when the frontend expects a specific enum). Use Zod to parse and narrow at the point the data enters the app:

```ts
import { z } from 'zod';

const practiceMode = z.enum(['case_understanding', 'form_recall', 'simple_vocabulary']);
type PracticeMode = z.infer<typeof practiceMode>;

// In the query function:
const mode = practiceMode.parse(row.mode); // throws if invalid — surfaces DB inconsistency early
```

Place Zod schemas in a `schemas.ts` file alongside the hook that uses them. Keep schemas focused on the specific narrowing needed — don't create monolithic schemas for every DB table.
